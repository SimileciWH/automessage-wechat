# PRD — 船员打卡消息自动发送系统

## 背景与目标

操作者每天维护一份 Excel 表，记录 30+ 位船员的打卡次数和打卡内容评价。目前需要手动逐一生成消息并在微信中发送，耗时且重复。

本系统的目标：操作者每天只需更新 Excel 并导出 CSV，通过本地 Web 控制台完成文案生成、预览确认、微信自动发送，全程可审计可追溯。

---

## 用户角色

单一操作者，使用 Mac，微信桌面版 4.1.5.240 已登录。

---

## 核心功能需求

### F1 — 读取 CSV 数据

- 从 Excel 导出的 UTF-8 CSV 文件中读取数据
- 必须包含四列，表头名称固定为：`微信名称`、`姓名`、`打卡次数`、`评价`
  - `微信名称`：用于微信搜索的备注名（如 `[老][2026Q1][AI 编程] 好运-明烨`）
  - `姓名`：消息中的称谓（如 `明烨`），用于 `hello，明烨` 和日志记录
- 可选第五列 `message`：若已有内容则直接使用，不再调用 AI 重新生成
- Excel 导出时末尾可能存在多余空列（`,,,,,,`），自动过滤忽略
- 任何格式错误（缺列、编码问题、数据类型错误）需在启动时立刻报错退出，告知原因

### F2 — AI 批量生成个性化文案

- 调用七牛云 OpenAI 兼容 API（模型：deepseek-v3-0324）为每位船员生成一条微信消息
- API 连接参数从项目根目录 `.env` 文件读取：
  - `OPENAI_BASE_URL` — API 端点（`https://api.qnaigc.com/v1`）
  - `OPENAI_API_KEY` — 鉴权密钥
  - `OPENAI_MODEL` — 模型名称（默认 `deepseek-v3-0324`）
- 消息格式固定为以下模板（v1 初版，流程跑通后再迭代优化文案风格）：

  ```
  hello，[姓名]，你已经连续打卡 X 次，还有 Y 次就上岸啦。我看了你的打卡内容，[具体鼓励]
  继续加油！
  ----------
  [一句励志鼓励语]
  ```

  - 当打卡次数 ≥ 12 时：去掉「还有 Y 次就上岸啦」，改为祝贺达成上岸目标
  - 「具体鼓励」必须结合今日打卡内容评价，不得泛泛而谈
  - 整体风格：口语化、自然、积极，不加 emoji

### F3 — Web 控制台预览与确认

- 所有文案生成后在 Web 控制台以卡片/表格形式展示每位船员的消息
- 操作者可对每条消息进行：
  - **编辑**：直接在输入框修改文案内容
  - **重新生成**：单条调用 AI 重新生成
  - **跳过**：勾选/取消勾选该人员（替代原 CLI 的 SKIP_NAMES 交互）
- 全部确认后点击「保存」将最终文案写回 CSV（`message` 列）
- 确认无误后选择模式并点击「执行」

### F4 — 微信自动化发送

每位船员依次执行以下流程：

1. 激活微信窗口
2. Cmd+F 打开搜索，粘贴**微信名称**（CSV 第一列，非姓名称谓）
3. 等待搜索结果，检测 Contacts 区域
4. 验证 Contacts 区域**有且仅有一个**联系人结果
5. 点击该联系人进入对话窗口
6. 验证窗口标题与联系人姓名一致
7. 点击输入框，粘贴文案，Enter 发送
8. 验证输入框已清空（确认发送成功）
9. 等待冷却间隔后处理下一位

### F5 — FAIL 即停机制

以下任意情况发生，立刻停止全部自动化，不处理后续联系人：

| 触发条件 | 提示信息 |
|----------|----------|
| 搜索结果中 Contacts 区域不存在 | `FAIL: 未找到联系人「X」，请检查备注名` |
| Contacts 区域有 2 个或以上结果 | `FAIL: 「X」搜索结果不唯一，存在发错人风险` |
| 点击后窗口标题与姓名不符 | `FAIL: 「X」窗口标题验证失败` |
| 发送后输入框未清空 | `FAIL: 「X」消息发送未确认，请手动检查` |

停机后：保存已有日志，打印已完成/未完成的名单，退出程序。

### F6 — 跳过功能

- **固定跳过**：在脚本配置区设置 `SKIP_NAMES` 列表，每次运行均跳过（CLI 模式）
- **临时跳过**：在 Web 控制台通过勾选框管理（替代 CLI 交互）
- 被跳过的人在日志中记录为 `SKIPPED`，不计入失败

### F7 — 发送日志

- 每次运行在 `logs/` 目录生成一个 JSON 文件，文件名含时间戳
- 每条记录包含：姓名、状态（SENT / SKIPPED / FAIL / DRY_RUN）、文案内容、时间戳
- 程序异常退出前必须保存当前日志
- Web 控制台在发送完成后展示发送结果汇总

### F8 — 消息持久化到 CSV

- CSV 增加第四列 `message`，存储 AI 生成或人工编辑后的最终文案
- 操作者在 Web 控制台点击「保存」后，文案写回原 CSV 文件
- 后续重新打开同一 CSV 时，已生成的文案直接加载，无需再次调用 AI
- crew_sender.py 读取 CSV 时：`message` 列有内容 → 直接使用；为空 → 调用 AI 生成
- 每次发送的完整文案在日志 JSON 中同步保留，提供双重可追溯

### F9 — 本地 Web 控制台

#### 启动方式

- 双击 `start.command`（macOS），终端一闪而过后浏览器自动打开
- 服务仅监听 `localhost:5001`，不对外暴露

#### 视觉风格

- **航海控制台风格**：深海蓝黑底色，青绿荧光强调色，玻璃态卡片
- 背景有舰桥/雷达仪表盘的质感，状态指示器、进度条有信号波形动效

#### 主要界面区域

| 区域 | 功能 |
|------|------|
| 顶部导航栏 | 系统名称、服务状态指示灯、当前 CSV 文件名 |
| 左侧控制面板 | CSV 导入（拖拽/选择）、模式选择、全局操作按钮 |
| 主表格区 | 每人一行：状态徽章、姓名、打卡次数、消息预览、操作按钮 |
| 底部日志控制台 | 终端风格，实时展示执行进度（SSE 推送） |

#### 操作模式

| 模式 | 行为 |
|------|------|
| 正式发送 | 粘贴消息并按 Enter 发送 |
| 安全模式 | 粘贴消息到输入框，不按 Enter，由人工确认后手动发送 |
| Dry-Run | 仅执行搜索检测，不粘贴不发送，验证联系人是否存在 |

#### 核心交互流程

```
导入 CSV
  → 「全部生成」或逐行「生成」→ AI 调用 → 填入消息框
  → 逐行检查 / 手动编辑 / 单条重新生成
  → 「保存」→ 写回 CSV（message 列）
  → 选择模式 → 「执行」
  → 底部控制台实时显示进度
  → 完成后展示发送汇总
```

#### 实时进度

- 点击「执行」后，底部控制台以 Server-Sent Events 实时推送进度
- 每条进度格式：`[01/30] 张海涛 ... ✅ SENT` 或 `❌ FAIL: 原因`
- 发送完成后展示汇总：成功 N / 跳过 N / 失败 N

### F10 — 无感知服务生命周期

- 浏览器关闭后，前端停止发送心跳（每 5 秒一次）
- 服务端检测到心跳中断超过 20 秒，自动 `SIGTERM` 退出
- 若执行过程中浏览器关闭，等待当前发送完成后再退出（不强制中断）

---

## 非功能需求

- 每条消息之间默认冷却 4 秒，可在配置区调整
- CLI 模式（`python crew_sender.py`）保留，供高级用户或脚本集成使用
- 所有可调参数（打卡目标次数、冷却时间等）集中在脚本顶部配置区，有注释说明
- 支持 `Ctrl+C` 随时中断，中断后保存已有日志

---

## 不在范围内

- 不支持发送图片、文件或语音
- 不支持群聊发送
- 不支持 Windows 或其他微信版本
- 不自动读取或写入 Excel 文件（操作者手动导出 CSV）
- Web 控制台不需要登录认证（本地单用户工具）
